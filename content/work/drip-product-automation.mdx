[drip.ng](https://drip.ng) is a men's streetwear store for Nigeria. I built it as a single Next.js app: the storefront and a Payload CMS admin share one codebase and one Postgres database.

![The drip.ng storefront home page](/images/work/drip-home.webp)

## The problem

Adding a product meant filling in a long admin form. Someone had to write a title and a description, pick categories, upload and tag photos, set cost and selling prices, write the SEO fields, and then create a variant for every size and colour combination.

I had already shortened the worst part. In January 2026 I added a bulk variant tool to the admin: pick the sizes and colours, and it generates every combination, skips the ones that already exist, and lets you edit price and stock in a review table before saving. That helped, but each product still started with a blank form.

Meanwhile, everything needed for a listing already fit in a chat message: a few photos and a caption like *"High Quality Luxury Top Available 15k White 16k"*. So the goal became: let that message be the form.

## How it works

The seller sends photos and text to the store's WhatsApp Business number, then types **done**. The bot replies with progress updates and, at the end, one summary per product: title, cost and selling price, variants, categories, and a link to edit it in the admin.

Behind that there are four stages.

**1. Ingest.** A webhook receives each message from the WhatsApp Cloud API. It verifies the request signature, answers straight away, and does the real work after the response is sent. Only numbers on an allowlist are processed. Images are downloaded and stored immediately, because WhatsApp's media links expire within minutes. Messages are grouped into a session per seller, and repeated deliveries of the same message are ignored.

**2. Extract.** When the seller says they are done, a background job sends the whole session (every caption and photo) to a multimodal model in one call, using the Vercel AI SDK with structured output. The model decides how many products the session contains and returns each one with a title, description, meta description, categories, alt text for every image, variant types and options, and cost prices parsed from shorthand like "15k". The provider is a config switch, so I can move between OpenAI and xAI models without touching the pipeline.

**3. Build.** The job cleans the model's output, matches variant options against the ones that already exist, creates the product, and generates every variant combination. The selling price is never the model's job: it is calculated from the cost price and a store-wide markup.

**4. Report.** The product is published and the seller gets the summary and the edit link. If it fails validation, for example because it has no usable image, it is saved as a draft instead and the message says so.

## What went wrong, and what fixed it

Most of the work was in making the result dependable. These are the problems that shaped the design.

**The model invented IDs.** Early on, a product failed to save because the model returned an image ID that did not exist. Now the output schema is built per session, and every ID field is an enum of the real IDs in that session. The model cannot return anything else.

```ts
// Simplified: the schema is rebuilt for every session
const product = z.object({
  title: z.string(),
  images: z.array(z.enum(imageIdsInThisSession)).min(1),
  categories: z.array(z.enum(categoryIds)).min(1).max(3),
  // ...
});
```

**Photos were attached to the wrong colour.** With several images in one prompt, the model sometimes attached an ID to the photo next to it. Wrapping each image in explicit opening and closing labels that carry its ID fixed that.

**Variant options multiplied.** The model would create "Black" when "black" already existed, and the option list grew out of control. Options are now matched to existing ones by a normalised label, and only the ones that are really missing get created. I wrote scripts to merge the duplicates that had already built up.

**Retries repeated work.** The first version did everything inside the webhook request. I moved it to a queued workflow where each stage is stored once it completes. A retry picks up from the last finished stage, so the model is not called twice and no product is created twice. If one product in a session fails, the others still go through.

**Failures were invisible to the seller.** Errors are now sorted into billing or quota problems and technical ones, and the seller gets a matching WhatsApp message. A failed session can be re-queued from the admin.

**Prices in SEO copy went stale.** The meta description is written with a price placeholder, which is filled in with the live selling price when the page renders. Changing the markup re-prices the catalogue without leaving old prices in search snippets.

The whole workflow is covered by integration tests: retries that do not call the model again, no duplicate products, partial failure, and the draft fallback.

## Trade-offs

- **Review happens after publishing.** For most of the project, products were saved as drafts for someone to check. They are now published straight away, and the summary message is the review step. That is faster, and it only became reasonable once the fixes above were in.
- **There is no custom screen for this.** The interface is the chat the seller was already using, plus the standard admin for edits. The frontend work in this project is elsewhere: the bulk variant tool, an optimistic cart, and a storefront built on Next.js Cache Components.
- **I did not measure the old flow.** We never timed product creation in the admin before the change, so I have no before-and-after number to quote. Next time I would record that first.
