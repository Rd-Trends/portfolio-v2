People looking for a home in Nigeria start on Google. For [Giddaa](https://giddaa.com), ranking for those searches matters more than any other channel, and almost all of the work to get there is frontend work: what the server sends, how URLs are shaped, and what a crawler can understand without running JavaScript.

Giddaa now appears on the first page of Google for property-for-sale searches in Nigeria. This is what I built on the buyer site to get there.

![The houses for sale page on giddaa.com](/images/work/giddaa-listings.webp)

## Lists that crawlers can read

The house lists used to load their content in the browser. The HTML a crawler received contained no listings. I moved the first page of every list to the server and added real paginated URLs (`/houses-for-sale/page/2`), each with its own canonical. Infinite scroll still works for people, and it continues from whichever page they landed on.

## Browse pages from one registry

Searches like "3 bedroom duplex in Lekki" need a page of their own. The first version, which I built in 2025, had a separate route for each combination: 33 route files and 15 screens.

In August 2026 I replaced all of it with one catch-all route driven by a registry of six facets: location, house type, bedrooms, purchase plan, finishing level and price range. The registry is the single source for the routes, the page titles, the internal links and the sitemap, so they cannot disagree.

The rules that keep those pages worth indexing:

- **At most two facets per URL**, so the number of pages stays bounded.
- **One URL per combination.** Facets have a fixed order, and any other order gets a permanent redirect to the canonical one.
- **Unknown values return a 404**, not an empty page.
- **Pages with no houses are marked `noindex, follow`**, and location pages only exist for areas that have houses.

The rebuild deleted 5,286 lines of code and kept the sitemap at exactly the same 2,275 URLs.

## Structured data as one graph

Each page used to emit separate JSON-LD blocks that did not refer to each other. Now every page emits one connected graph. `Organization` and `WebSite` are declared once in the root layout, and every other node points to them by `@id`.

A listing page describes the house as a `RealEstateListing` with an `Offer`, address, coordinates, floor area and amenities. Its finance plans are described as `LoanOrCredit`, and its questions as an `FAQPage`. Browse pages use `CollectionPage`, `ItemList` and `BreadcrumbList`. The schemas are typed with `schema-dts`, so a wrong property fails the build, not a rich results test weeks later.

Breadcrumbs are built from one array that feeds both the visible trail and the JSON-LD.

## Sitemaps, redirects and index hygiene

- **Segmented sitemaps.** A sitemap index points to separate sitemaps for static pages, browse pages, houses, estates, land and articles, paged at 1,000 URLs each. The browse sitemap is generated by the same function that enumerates the routes.
- **Legacy URLs.** The site had 1,584 old URLs that needed permanent redirects. A Bloom filter in the request proxy checks each path first, so the redirect table is only consulted when there is likely to be a match.
- **Thin pages kept out of the index.** Filter and sort states get an `X-Robots-Tag` header. Duplicate pages were removed.
- **One social image per page.** Every page emits a single 1200 × 630 image, which also fixed link previews in WhatsApp.
- **AI crawlers.** `robots.txt` names them explicitly, and an `llms.txt` is generated from the same facet registry.

## Fast pages that stay fresh

The site runs on Next.js Cache Components. Most routes are static or partially prerendered, and the first 500 house pages are built ahead of time. Published content is cached for a day. When a listing changes, the backend calls a signed webhook that expires just the cache tags for that listing, so an edit shows up without rebuilding anything.

Images moved to Cloudflare R2 with a proper `srcset` and `sizes` for each place they are used.

## Credit and what is next

This was not solo work. Teammates built the blog sitemap and wrote the SEO specs for the resources section.

A copy review of every browse page found titles longer than Google displays and meta descriptions that are too similar from page to page. Rewriting those templates, with live inventory counts in the descriptions, is the next job.
